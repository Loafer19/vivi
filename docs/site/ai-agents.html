Set up in two minutes

Enable remote control

Off by default. Turn on Settings → Controls → Remotes → Allow AI agents and scripts (General → Remote control before 0.15) and restart Vivi, or run VIVI_IPC=1 vivi once.

Get vivi-mcp

It ships with Vivi: Arch installs /usr/bin/vivi-mcp, Flatpak /app/bin/vivi-mcp, cargo build --release gives target/release/vivi-mcp.

Add it to your client

Paste the config below and restart the client. vivi-mcp --help prints the socket path it uses.

Add it to your client

Every client runs the same command: /usr/bin/vivi-mcp (or the path from which vivi-mcp / target/release/vivi-mcp). GUI apps often have a minimal PATH, so an absolute path is safest.

~/.config/Claude/claude_desktop_config.json
{
  "mcpServers": {
    "vivi": { "command": "/usr/bin/vivi-mcp" }
  }
}

Restart Claude Desktop; the vivi tools appear in the tools menu. Windows is not supported yet (Vivi's control socket is a Unix socket).

~/.cursor/mcp.json (global, Linux and macOS) or .cursor/mcp.json in a project

{
  "mcpServers": {
    "vivi": { "command": "/usr/bin/vivi-mcp" }
  }
}

One command, available in every session (add --scope project to share it via .mcp.json):

claude mcp add vivi -- /usr/bin/vivi-mcp

.vscode/mcp.json in your workspace

{
  "servers": {
    "vivi": { "type": "stdio", "command": "/usr/bin/vivi-mcp" }
  }
}

Windsurf, Zed, Continue, Cline, … any client that launches stdio servers works with the same command. If it does not inherit XDG_RUNTIME_DIR, pass the socket explicitly:

{
  "mcpServers": {
    "vivi": {
      "command": "/usr/bin/vivi-mcp",
      "env": { "VIVI_SOCKET": "/run/user/1000/vivi.sock" }
    }
  }
}

Flatpak: run it through the sandbox instead:

{
  "mcpServers": {
    "vivi": {
      "command": "flatpak",
      "args": ["run", "--command=vivi-mcp", "io.github.loafer19.vivi"]
    }
  }
}

How it works

A separate small binary that speaks MCP over stdio and forwards tool calls to Vivi through a private local socket. It depends on nothing but std and serde_json; there is no network listener and nothing leaves your machine.

Tools

Resources vivi://status and vivi://playlist (JSON) are also exposed. So are vivi://recent, vivi://lyrics and vivi://plugin-commands, with change notifications for all of them; there are also prompts (play_radio, fix_subtitles, …), tool annotations so clients ask before destructive calls, argument checks, pagination, and MCP 2026-07-28 next to the handshake versions.

Security

Off by default. Nothing listens until you turn on Allow AI agents and scripts.
Local only. The socket is $XDG_RUNTIME_DIR/vivi.sock (fallback ~/.cache/vivi/vivi.sock, override with VIVI_SOCKET), created with mode 0600, so only your user can connect. There is no TCP or HTTP listener.
Limited reach. Agents can control playback and read what is playing; plugin settings cannot be read or changed (agents can run the commands plugins add to menus; clients ask first, since those tools are marked destructive). Anything an agent opens plays with your user's permissions, so keep the usual care with untrusted URLs.

Troubleshooting

“Vivi is not running” or connection refused
Start Vivi with Allow AI agents and scripts on (Settings → Controls → Remotes; restart after changing it) or run VIVI_IPC=1 vivi. Only one Vivi instance owns the socket.
The client cannot find the socket
Some clients do not inherit XDG_RUNTIME_DIR. Pass it explicitly: "env": { "VIVI_SOCKET": "/run/user/1000/vivi.sock" } (check the path with vivi-mcp --help).
“command not found: vivi-mcp”
Use the absolute path (/usr/bin/vivi-mcp or target/release/vivi-mcp); GUI clients often have a minimal PATH.
Test without an AI client
npx @modelcontextprotocol/inspector vivi-mcp, or by hand: 
printf '%s\n' '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"get_status","arguments":{}}}' | vivi-mcp
echo '{"cmd":"status"}' | socat - UNIX-CONNECT:$XDG_RUNTIME_DIR/vivi.sock
search_streams is slow or empty
It queries radio-browser.info and iptv-org over the network and can take a few seconds.
Windows
Not supported yet: the control socket is a Unix socket (Linux and macOS). Only the stdio transport is available.
